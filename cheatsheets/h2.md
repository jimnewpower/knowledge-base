# H2 database cheat sheet

> Baseline: H2 2.x embedded JDBC; pin a patched release compatible with the application. Reviewed: 2026-09-25.

H2 is useful for small embedded stores and fast tests. A compatibility mode is a convenience, not proof that SQL will behave identically on Oracle or another production engine.

Related: [SQL](sql.md), [Oracle](oracle.md), [testing](testing.md), [database migrations](database-migrations.md).

## JDBC URL choices

| URL | Behavior |
|-----|----------|
| `jdbc:h2:mem:` | Private unnamed in-memory database for the connection |
| `jdbc:h2:mem:unit_test` | Named in-memory database shared by matching connections in the same JVM/class-loader environment |
| `jdbc:h2:mem:unit_test;DB_CLOSE_DELAY=-1` | Keep the named database after the last connection closes; explicitly manage cleanup |
| `jdbc:h2:file:./data/catalog` | Persistent files relative to the process working directory |
| `jdbc:h2:file:./data/catalog;IFEXISTS=TRUE` | Fail rather than silently create a new store if absent |

The default close behavior can make an in-memory database disappear between setup and test if all connections close. The opposite setting can leak state between tests. Assign isolated names or deliberately reset each test's owned database.

## Small SQL fixture

Execute on a fresh test database through a JDBC/SQL client. This creates and populates a table; it is not a production migration.

```sql
CREATE TABLE observation (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    station VARCHAR(80) NOT NULL,
    reading NUMERIC(12, 4) NOT NULL
);
INSERT INTO observation (station, reading) VALUES ('test-station', 12.5000);
SELECT station, reading FROM observation ORDER BY id;
```

## Testing boundary

H2 tests can check basic repository wiring and small fixtures. Run target-engine tests for dialect SQL, generated keys, constraints, transaction isolation, locking, timestamp handling, pagination, and migrations. A green H2 test cannot validate an Oracle query plan.

Do not add compatibility flags indiscriminately to make a migration test pass. Record why each setting exists and keep production-only SQL visible. The H2 1.x-to-2.x boundary requires migration planning; follow the documented export/import route for the exact releases and validate the restored data.

## Embedded operation

Use an explicit application data directory and close pools during shutdown. Do not casually copy live database files as a backup; use documented backup/export procedures and test restoration. Avoid exposing the H2 console or TCP server as an accidental production administration interface. Keep credentials outside JDBC URLs when those URLs are logged.
